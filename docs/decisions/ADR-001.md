# ADR-001: Independent canonical ANDES with a Codex-first adapter boundary

**Status:** conceptual direction accepted in Design v0.1 (1.1-1.4, 1.6, 5.1, 10.2); this record is a review draft. Native implementation choice remains open for A2.1. Date: 2026-11-26.

## Context

The lab needs portable, versioned methods with native Codex usability, researcher-selected profiles and controlled release evolution. ECx already provides useful methods but is a personal experimental harness; ANDES must not require its runtime or account configuration. The target ANDES repository is greenfield. No native adapter or packaging capability has yet been demonstrated in it.

## Decision

Maintain ANDES as an independent repository with a compact mandatory core and on-demand compatible profiles. Canonical norms, principles, skills, playbooks, roles and contracts are runtime-neutral. A small Codex adapter translates only the supported and verified representation into native discovery/execution. A project pins immutable release/profile identities. Adapt upstream components selectively after source/license/provenance review. Preserve Neruda's standalone boundary and ECx's independent experimentation. Create deterministic tooling only where necessary for correctness, reproducibility or enforcement.

This decision does not select a language, package manager, install layout, native file format, CLI, orchestration engine, service or database. A2.1 compares actual native options in isolated test homes and records a follow-on ADR for the minimal adapter/packaging decision. Do not assign ADR-001 to a contradictory new decision silently; use the next available number or amend through review.

## Options considered

| Option | Benefit | Cost / risk |
|---|---|---|
| Extend ECx directly | Fast reuse of familiar code and configuration | Couples shared lab release to personal harness, incomplete evaluator and account assumptions |
| Adopt an upstream stack wholesale | Many existing capabilities immediately | Duplicated instructions, incompatible runtimes, unreviewed licenses and non-proportional context |
| Independent canonical stack + thin first adapter (selected) | Controlled provenance and versions; portability; incremental installation | Requires inventory, translation and real compatibility tests |
| New generic orchestration runtime immediately | Maximum control over mechanics | High complexity, duplicated native capabilities, premature security burden |

## Rationale and consequences

Separation of canonical meaning from runtime-specific discovery limits migration cost and avoids forcing researchers to adopt personal tooling. It makes source adaptation and profile composition inspectable. Native runtime limitations are honest blockers: unsupported functions stay disabled. The initial scope is local-first and no mandatory server. Need release/version identity, manifest, compatibility, non-destructive installer and rollback evidence before claiming distribution works. No broad Docker or language stack is selected.

## Risks and validation

A1.2 verifies source terms, exact paths and adaptation boundaries; A1.3 tests unique IDs, dependency compatibility and metadata. A2.1 probes native discovery, precedence and role invocation in temporary homes with exact versions; test fresh/upgrade/conflict/rollback before release. G5/G6 additionally require enforced execution/evaluator isolation, not mere instructions. Record all unsupported observations and ask the maintainer before material dependency changes.

Revisit if native discovery cannot satisfy mandatory core/profile requirements, managed install cannot preserve user configuration, or measured integration complexity warrants a different adapter/packaging boundary. Cross-harness adapters or a coordination service require separate evidence of need. Stable policy changes require human approval.
