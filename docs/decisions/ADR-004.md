# ADR-004: Start with a project-local Codex candidate projection

Status: accepted by the maintainer in chat on 2026-11-28, following independent review of A2.1. Proposed date: 2026-11-27. Baseline `1c77c37`; follow-on to ADR-001, not a replacement of its portable canonical boundary. Acceptance approves the project-local candidate strategy and stated limits; it does not establish the untested native behaviors.

## Context and observations

The isolated native spike observed Codex CLI 0.172.0 discovery of project/user skill folders and minimal name/description metadata. A temporary thread exposed the documented instruction-source ordering and nested override selection without starting a model turn. A role declaration was accepted as configuration metadata; actual role execution and packaging installation remain unverified. These observations are specific to macOS arm64.

## Options and decision

1. **Project-local native skill projection in a candidate fixture — recommend now.** Project discovery is observed and keeps experiments away from personal skills/configuration. Translate only the verified name/description/path representation; retain canonical content and component identity outside the adapter. Keep constitution and router pointers compact; component inclusion does not imply eager instruction loading.
2. **Native plugin bundle — defer pending installation probes.** Plugin/marketplace commands exist and official documentation describes packaging, but command availability does not demonstrate non-destructive installation, composition, pinning or rollback.
3. **Global skill/config installation — defer.** User discovery is observed, but global ownership, collisions and rollback are not. Do not overwrite or merge personal instructions/configuration.
4. **Custom agent orchestration/runtime — reject for this foundation slice.** Nothing in the observed minimum requires an orchestration service. Metadata acceptance does not demonstrate role execution, budget containment or autonomous safety.

The recommendation authorizes no production installer or canonical release. A1.5 should use the smallest isolated native fixture and must separately demonstrate direct invocation, routing and selective loading. Unsupported or untested capabilities stay disabled; an accepted ADR is not native execution evidence.

## Consequences and validation

Keep native metadata/path rules in the adapter and protect runtime-neutral catalog identities. Build A2.2 resolution against the accepted catalog/provenance contracts, with exact immutable inputs and explicit environment compatibility. File ownership/collision handling, distribution format and upgrade/rollback remain separate implementation decisions gated by real tests.

Prefer reference/pointer projections over duplicating canonical policy; investigate relative-reference resolution in the actual invocation fixture before relying on it. Do not install symlinks or copy content into real homes based on this decision.

Evidence: `docs/evidence/a2-1-result.json`, the executable probe and its candidate manifest. Independent review and human acceptance are required. Revisit after native-version changes, failed direct-invocation/reference-loading checks, a demonstrated need for plugin packaging, or a supported-platform requirement beyond the observed environment. No live model call, new dependency or private-data access is introduced here.
