# ADR-002: Local canonical catalog validation

Status: proposed implementation for maintainer acceptance under A1.3. Date: 2026-11-27. References: ADR-001; accepted A1.2 report; Design 1.1–1.4, 1.6, 2.1, 5.1, 10.1, 10.3.

## Decision and alternatives

Use a runtime-neutral JSON document, JSON Schema draft 2020-12 for structure, and a small Python semantic validator for local graph/composition/provenance checks. Use Python 3.12+, uv and a locked jsonschema dependency in a project-local environment. The maintainer selected Python/JSON Schema during planning. This is verification tooling, not the runtime/installer language decision.

JSON Schema alone cannot check reference closure or graph conflicts. A hand-written structural validator would duplicate a standard schema engine. Node/Ajv is a viable alternative but would add a second selected tooling stack without a current need. A package/release resolver is deliberately deferred: one local version per stable ID and exact local references are sufficient for this task.

## Consequences and boundaries

Profiles are additive; explicit conflicts fail rather than silently choosing precedence. Mandatory core cannot be removed. Provenance requirements distinguish original content from reviewed upstream imports; the inventory may contain blocked material that the eligible catalog rejects. License identifiers are a bounded allowlist, not automated legal approval. Native metadata, actual skill syntax, task/evidence contracts and release resolution remain separate.

Dependencies are locked with artifact hashes in uv.lock. No system-wide installation, runtime service, private data, live model call, GitHub settings change or release is introduced. The fixtures are synthetic and not installed skills. Contract changes require review and fixtures; unknown schema versions fail rather than silently migrating.

## Validation and revisit triggers

Use the positive fixture, independent negative cases, direct selection, dependency closure, combined-profile conflicts and path boundary checks documented in the catalog contract. Independent review and human acceptance are required. Revisit when accepted native findings expose a necessary translation change, a real profile needs license expressions/version ranges, or a downstream contract needs cross-document references. Do not introduce those mechanisms speculatively.
